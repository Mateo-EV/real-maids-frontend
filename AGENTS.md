# Agent instructions

Mandatory guidance for coding agents and automation working on The Real Maids frontend.

## Read first and establish evidence

Read [README.md](README.md), [the product guide](docs/README.md), and this file before changing code or documentation. Then inspect the relevant `package.json`, `angular.json`, `components.json`, TypeScript configuration and source/tests.

- Source, configuration and observed test results establish implementation status; installed dependencies, empty files, types and tokens do not establish completed features.
- This file preserves the accepted technical constraints; the product guide preserves RF/RNF/HU/M/P intent, not implementation evidence.
- Actual backend OpenAPI/Swagger establishes REST contracts; approved Figma designs establish visual references.
- Do not silently change product scope or resolve open questions. Major changes to framework, UI, state, forms, SSR, test runner or cross-cutting architecture require an explicit human decision, recorded here as appropriate. No separate ADR process is required.

## Tools: discover availability, then use local fallback

Do not assume any agent-specific configuration or MCP server is installed. Discover the tools actually exposed by the current environment and report unavailable capabilities or failed calls.

**Angular CLI MCP**, when available, is preferred for Angular work:

1. Run `list_projects` first to discover the workspace and targets.
2. Consult `get_best_practices` before modifying Angular code.
3. Use `search_documentation` for Angular APIs and syntax.
4. Use `run_target` for configured build/test targets.
5. Use the exposed dev-server tools for serve cycles.

If the server or required operation is unavailable or fails, record the limitation and use the workspace-local Angular CLI (`npx ng ...`) or supported npm scripts, never a global CLI. Use Angular schematics for ordinary artifacts when appropriate. Available targets are `build`, `serve` and `test`; do not assume lint or E2E targets.

**Code intelligence MCP**, when exposed (for example Codebase Memory or CodeGraph), can support structural discovery. Discover the actual API, check index status/root/coverage where supported, and confirm relevant findings against source. Tool names such as `list_projects`, `index_status` and `check_index_coverage` are server-specific, not universal requirements. If unavailable, use read-only source/configuration inspection; do not claim graph coverage or infer absence from an incomplete index.

**Spartan CLI:** before adding UI, run:

```bash
npx ng generate @spartan-ng/cli:info --json
```

Reuse installed Helm components; generate missing available components with `npx ng generate @spartan-ng/cli:ui --name=<component>`. Do not guess selectors or manually copy component implementations.

## Architecture and current boundaries

- Angular 22 standalone with TypeScript 6; bootstrap through `bootstrapApplication`, strict typing and the configured `@/*` alias. Use explicit DI/providers and avoid `any`.
- Angular SSR + Express and client hydration are part of the platform. `/login` uses prerender; all other routes currently use client rendering. Review route render modes when real backend sessions are introduced. Guard or abstract browser-only APIs for server execution; do not assume a hosting provider.
- Organize business capabilities under `src/app/features/{auth,customers,users}`, independently of their audience (RNF09/RNF10). Use `domain`, `application`, `infrastructure` and `presentation` only when they protect real boundaries; avoid empty scaffolding and speculative role directories.
- Dependencies point toward domain contracts. Put feature error types in `domain/errors`; domain contracts must not import from `application`. Angular `InjectionToken` and RxJS `Observable` coupling in domain repository contracts is intentional; do not remove it as part of a structural refactor.
- Represent each application action with a `*UseCase` exposing `execute()`; do not group feature actions into `*Service` classes. Keep use cases stateless and HTTP/storage adapters in `infrastructure`, not visual components. Bind repository implementations at the composition root, using `InjectionToken` where appropriate. By explicit user decision, infrastructure repository implementation classes implement the domain interfaces and inject root-provided sources; auth, users, the role catalog, RBAC, IAM sessions and audit inject HTTP sources, while customers retains its in-memory source. Sources do not implement domain repository interfaces. Bind tokens with `useExisting` to root-provided implementations, preserving shared source instances. Keep this boundary for auth, customers, users and roles; do not bind domain tokens directly to sources. In-memory latency must precede validation, mutation, ID allocation and storage writes so unsubscribing before execution prevents effects.
- Keep capability routes, pages, guards and stores with their feature. Auth owns `/login`; `src/app/experiences/admin/admin.routes.ts` owns the protected `/admin` shell and lazy child routes, reusing the auth guard. The empty child temporarily redirects to `users`; this is not P02. Keep shared brand/session/logout in the shell and IAM catalog tabs/actions in the users page. IAM is the only enabled sidebar route; other module entries remain disabled non-navigating buttons. `app.routes.ts` composes both lazy route sets and existing login redirects. Reserve `core` for cross-cutting configuration/singletons and `shared` for genuinely reusable pieces.
- Use NgRx SignalStore for demonstrated shared presentation state per feature, not a monolithic global store. `AuthStore` and `CustomersStore` remain root-provided in their feature's `presentation/state`; do not change provider/store lifetimes implicitly. `AuthStore` delegates to `LoginUseCase`/`LogoutUseCase` and restores through `GetCurrentUserUseCase`/`AuthRepository.me()` before auth or guest guards decide. Preserve only a valid loaded session; access expiry is renewable and must not be confused with the fixed session/refresh deadline. Clear credentials/state on session expiry or logout, reject stale login/restoration/refresh/401 completions and mirror credential changes through application/domain contracts. The user superseded memory-only storage with temporary localStorage persistence for BOTH access and refresh: use versioned, origin-bound, browser-guarded validation; reload identity must come from real `GET /api/auth/me`, never a stored profile/demo flag. Both credentials are JavaScript-readable and exposed to XSS. Refresh is public JSON, rotates once, cannot extend the session and needs same-tab single-flight plus origin-wide Web Locks; fail closed if coordination is unavailable. Explicit logout clears locally immediately and attempts bounded documented revocation without promising remote success; expiry/destruction/starting login are private invalidations, not remote logout. SSR/prerender must neither access storage nor establish shared credentials/auth requests/transfer-cache tokens. The old in-memory demo source and memory-session adapter remain unwired, never fallbacks. Consume validated nested profile fields without invented IDs, permissions or role-name/JWT inference; backend authorization remains authoritative. Permanent persistence/cookie transport remains open. Local form state remains local.
- Use Angular Signal Forms: signal model, declarative `form()` validation, `formRoot`/`formField`, reactive errors and `submit()`/`submitting()`. Do not introduce generic form wrappers without repeated real needs.
- Use Spartan Brain/Helm + Tailwind CSS 4, not Angular Material or Bootstrap. Helm is maintained locally in `libs/ui`, imported through `@spartan-ng/helm/<component>`; `components.json` configures generation and `src/styles.css` holds semantic theme tokens. Primary actions use global navy/foreground and shared enabled hover across users, overlays, login and admin; retain gold accent and coral decoration. Do not duplicate primary overrides in feature hosts.
- Users owns Hot Toast JavaScript and configuration at its lazy route: explicitly provide `HotToastService` and `provideHotToastConfig()` together with `ViewService`, whose injector creates the body-attached toast container. Do not move configuration alone or resolve the container through the root service. Keep toast CSS global in `angular.json` for body overlays; repository/store lifetimes and bundle budgets remain unchanged (RNF04/RNF09/RNF10/RNF12).
- M03 uses `customers`/`Customer*` naming. Demo data stays in `customer-in-memory.source.ts`. Its five CRUD/query use cases and `CustomersStore` are not a P04 screen or backend contract.
- Use `DestroyRef`/`takeUntilDestroyed` for component-owned requests; do not couple root store lifetimes or unrelated consumers to a component's destruction. Guard post-await feedback/navigation against destruction. Legacy users and roles demo records remain unwired from real catalog/CRUD repositories and live directly in their corresponding in-memory source files, with matching stable role IDs, max-ID-based allocation and defensive date copies. Page entry runs independent listing, roles, statistics and count queries with component cancellation; do not reintroduce initializer or sequential CRUD seeding complexity. Server-side source fixtures do not create an auth session. User dialogs route outside-click and Escape through guarded Cancel: allow idle dismissal, disable Cancel and prevent dismissal while pending. Preserve accessible names on icon-only actions. No role-management button or modal is exposed; retain role contracts/store and user role selection. Real role administrative mutations return `UNSUPPORTED`, never demo writes. By explicit user approval after backend commit `9439829`, retire the fixed 500-user catalog and first-1000 global session read. One root UserStore owns writes and reactive query-keyed entries (result, loading, refreshing, error, freshness and effective query metadata), never a complete users/loaded/loadUsers catalog. Interface controls own only query signals and lifecycle-scoped observation subscriptions; pure readonly projections select entries, without a UserListStore, copied writable read state, fixed consumer namespaces or a singleton current query. Cache normalized full queries for 120000ms, checked on reads without polling; retain at most 20 variants (a small navigation/search history), share ref-counted in-flight reads and fence invalidated/session-old completions. Same-query interfaces select the same reactive entry; different query keys remain independent. Active views are pinned during history eviction. Admission beyond twenty distinct concurrent observed/in-flight keys rejects rather than evicting an active view; current Users/Audit interfaces need at most two. Logout, expiry or session replacement clears cached and visible user data; access credential renewal within the same identity/deadline does not. SSR dispatches no user reads. Keep legacy getUsers only in unwired fixtures; RoleInMemorySource checks UserInMemorySource directly, never the production repository. Asynchronous statistics, actor options, session owners/details/counts use SignalStores, not component result caches. The Users listing retains its shared pagination contract: UserListQuery extends shared PaginationParams (optional offset/limit, default 0/20) and results directly use PaginationResponse<User> (items/total/offset/limit), without a duplicate page type. Only the HTTP source maps documented busqueda/idRol/activo and aligned offset/limit to pagina/tamanio; validate safe integers and emitted int32 bounds without applying normalizePagination's unrelated maximum 100. Initially request ten rows, adopt the actual returned offset (page times effective size) and effective limit in active query state, and derive server filtered page counts/ranges from total/offset/limit without local filtering or slicing. Navigation and bounded out-of-range recovery retain that effective limit; do not assume backend effective-size stability across requests. Keep the Users query controls independent from Audit's actor query controls, both selecting root UserStore entries. Dialogs receive selected User context and use mutation actions only; role initialization and retry remain independent of listing/statistics/counts. Search is debounced; filters reset to page zero, obsolete requests are cancelled, and an empty out-of-range page gets at most one clamp/refetch. Hide rows from unrelated queries on pending/error. Same-query background refresh, including revisits to expired cached queries, preserves prior rows with a visible updating status or retryable stale-data error. Expired entries remain within the same 20-variant cap; only successful reads renew TTL, never cache access or failed revalidation. Successful writes and PARTIAL_UPDATE invalidate all cached variants and refresh subscribed Users/Audit list consumers without blocking loading or clearing same-query rows. They increment UserStore.mutationRevision once, preserving partial errors; count/owners consumers refresh with component cancellation, never double-refreshing lists, replaying writes or creating orphan root subscriptions. UserStore also owns one reactive global statistics entry from GET /api/usuarios/estadisticas, with result/loading/refreshing/error/expiry independent of list and mutation statuses. Readonly projections select it; there is no page-provided UserStatisticsStore. Statistics reuse successful reads for 120000ms, checked on reads without polling; only server success renews TTL. Expired revisits and forced retries retain verified counts with updating or retryable stale-error feedback, including verified zero. Statistics reads share ref-counted cancellation; success/PARTIAL_UPDATE invalidates statistics and refreshes active observers once, not through a duplicate page mutationRevision reload. Component subscriptions own activity; inactive statistics never self-refresh. The existing UserStore auth generation clears and fences statistics on logout/expiry/replacement, not same-session renewal; SSR dispatches no statistics reads. Never label current-page counts global. Age is removed from users. Preserve password bytes: required documented validation on create, blank edit means unchanged, nonempty edit uses the dedicated password endpoint. Profile/status/password updates are sequential and non-atomic; report partial updates, refresh server state and never replay writes. T4 RBAC consumes real dynamic permission IDs/codes/modules/descriptions and atomically replaces the whole assignment, including empty arrays. Preserve assigned IDs absent from the catalog, validate duplicate IDs/codes and target identities, and never infer CRUD columns, configured flags or navigation ACL from roles. Backend 403 is authoritative: do not equate all delSistema roles with uneditable roles. Keep permission confirmation/draft/loading guards and cancellation. Its legacy illustration source/dialog remain unwired, never fallbacks. T5 IAM sessions use server-paged GET /api/sesiones/usuarios summaries with name/email search, Todos/Con sesiones/Sin sesiones and initial five-owner pages. Use shared offset/limit and effective returned metadata with bounded recovery. Native accessible disclosures alone request GET /api/usuarios/{id}/sesiones, with independent loading/error/retry. Exact global counts come from GET /api/sesiones at page 0 size 1, never owner totals, array lengths or local expiry. Validate DTOs, metadata, unique IDs, owner identity and caller-relative actual flags. Loading/error/cancellation leaves counts unverified, failures visible and retryable, never false empty or demo fallback. Never correlate credential markers with server session IDs or invent profiles/counts; no initial N+1 detail reads. Individual current revoke directs to Logout (backend 400); empty successful 200/204 closed/expired revocations are accepted. After session writes refresh active owners, exact count and affected open detail at most once per read without replay or optimistic totals, leaving refresh failures visible; bulk self-revoke preserves current and remains repository/use-case/store-only, without a new launcher. T6 actor filtering owns independent local query controls and observes/selects root UserStore entries with debounced server name/email search, paging, labeled Helm selection, email disambiguation and secondary IDs. Only selected loaded options supply numeric userId; typed search queries options but never applies audit identity. Preserve chosen ID/name/email across retained visits and query gaps, with visible loading/errors, cancellation and All actors/reset. Historical/deleted actors may be absent; user catalog membership never constrains audit records, totals, detail or CSV. T6 audit uses real queries/detail and filtered totalGlobal-independent paging, inclusive UTC date ranges and raw server CSV with the documented 10,000-record cap. Never rebuild export from cached rows or claim formula/header/browser acceptance. Legacy session/audit sources remain unwired, never fallbacks. Preserve root lifetimes, component cancellation and guarded feedback; cancellation cannot roll back dispatched backend writes.
- Current lazy routes are `/login`, temporary protected `/admin` and `/admin/users`. Auth/guest guards exist; role authorization does not. T2 wires a functional origin-scoped auth interceptor explicitly with `withInterceptors`. `API_URL` is bound to public build-time configuration and `provideHttpClient()` supplies Angular 22's default fetch transport. Environment labels do not define health checks. The shell explicitly distinguishes IAM demos from real login; best-effort logout does not certify backend revocation. Its custom Spartan language select uses domain `Lang` with Spanish default and visual-only English choice; do not add translation, persistence or session mutation implicitly (M02/RF02/HU02/P03, RNF06/RNF08/RNF09). ## Security and backend integration

- Angular consumes only the internal REST/JSON API; require HTTPS in production. Backend business validation and authorization are authoritative. Role-aware navigation and private-route protection improve UX but do not authorize requests; never infer a complete ACL from role names or planned landing screens.
- Never call QuickBooks Online directly from Angular or bundle client secrets, private credentials, refresh tokens or backend secrets. QuickBooks OAuth, idempotency and reconciliation belong to the backend; frontend status/error/retry UI must use confirmed internal endpoints.
- Never log passwords, JWTs, payment data or other sensitive information. Handle 401/403 consistently without leaking data.
- Temporary localStorage persistence of access AND refresh tokens is explicitly approved and supersedes the former browser-memory-only policy. Do not adopt sessionStorage, cookies or another permanent transport implicitly; localStorage exposes credentials to XSS. Reject unusable/malformed/expired storage, and revalidate restoration through the backend rather than treating persisted data as permission authorization. Live authenticated requests/CORS and browser acceptance remain pending until a protected credential-input channel is available; never embed credentials in commands, fixtures or task artifacts. Public environment configuration may include an API base, never secrets.
- Before integration, obtain actual OpenAPI and confirm base URL/versioning, DTOs, errors, pagination, filters, date/time/timezone and enums. Do not invent endpoints, permissions, duplicate rules or retry semantics from demo data or the functional plan. Record contract differences/open issues in the product guide and test adapter/interceptor mapping, success and failure cases.

## UI and domain behavior

- Reuse Helm variants and semantic tokens. Maintain desktop/tablet/mobile layouts; prefer cards and visible actions over unadapted wide mobile tables.
- Preserve title/context/action hierarchy, accessible labels, required-field/help/error associations, keyboard navigation and focus. Register icons with `provideIcons` when needed; color must never be the only status signal.
- Distinguish loading, empty, error and success. Show progress during submission, prevent duplicate actions and confirm success only after the applicable operation succeeds. Confirm cancellations and permission changes with the affected record visible.
- Distinguish service requests from customer support. Use concrete action verbs and preserve useful record/filter context across navigation.
- Follow the business states in the product guide; do not invent reopenings or exceptional transitions.
- Prepare UI copy for Spanish/English; the i18n library/fallback and operational timezone remain open. Do not choose them implicitly.

## Quality and completion

After each change, run the workspace-local Prettier on the files you touched before final verification or commit preparation: `npx --no-install prettier --write <paths>`, followed by `npx --no-install prettier --check <paths>`. Respect `.prettierrc` and `.prettierignore`; do not format unrelated files unless explicitly requested. Run formatting before staging and snapshot approval, and never alter an approved snapshot silently.

Use the official Angular `test` target with Vitest, not Jasmine/Karma. Component schematics have `skipTests: true`; create required tests explicitly. Missing tests are not a successful empty suite; do not disable or weaken tests for a green result.

For code changes, compile and run relevant tests through available Angular MCP operations or local CLI. Cover domain edge cases, use-case success/failure, adapter mapping/errors, guard permissions and component validation/loading/error/actions as applicable. Validate SSR/hydration safety and responsive/keyboard behavior for UI changes, including recent Chrome, Edge and Firefox where relevant. Report exact commands and observed outcomes, not inherited test counts.

No E2E or CI/CD is currently configured. Adding E2E requires an explicit tool decision, a reproducible target and documentation; prioritize login, customer CRUD, request-to-assignment, mobile assigned services, allowed/rejected transitions, customer support and backend-only QuickBooks status flows.

A feature is complete only when connected to its consumer/route as applicable, compiled, proportionately tested, secure, permission-aware and equipped with the required data/UI states. Update the implemented/planned distinction and link meaningful behavior to an existing RF/RNF/HU/M/P identifier in the product guide; document missing traceability before implementation. For documentation-only changes, verify relative links, language and claims against source/configuration without asserting unrun builds or tests.
