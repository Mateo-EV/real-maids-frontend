# Customers and acquisition — real HTTP application boundary

M03/RF03/HU03 and RF12/HU12 now have customer HTTP sources, explicit root repositories, stateless named `*UseCase.execute()` actions and a session-scoped root `CustomersStore`. There is **no customer route, screen or P04 delivery**. Acquisition still lacks a more specific inherited RF/HU identifier; this implementation follows the approved customer integration scope, not an invented requirement.

Contract evidence: backend `feat/customers-integration`, commit `68fd59d61544629e2d9f9245a4692dba96d980d9`; actual controllers, `CaptacionDtos`, `ClienteRelacionDtos`, extended `ClienteResponse`, `PropiedadRequest/Response`, `AtencionDtos.HistorialClienteResponse` and `HistorialClienteService`. Local HTTP testing is not live backend acceptance.

Every token is bound with `useExisting` at `core/config/app.config.ts` to a distinct root `*RepositoryImpl` implementing its domain interface and injecting its root HTTP source. Sources do not implement domain repositories. [Application actions](application/use-cases/) delegate without state or retries; [HTTP sources](infrastructure/source/) own validation/mapping. Small feature-local pure helpers share repeated DTO/input checks; no generic CRUD base or cache framework was added.

## Types and write semantics

Angular uses `Lead`, `LeadOrigin`, `LeadFollowUp` and `leadId` internally, including quote and web-form links. Sources translate the unchanged Spanish `idProspecto`, `/api/prospectos` and `/api/catalogos/origenes-prospecto` wire contract; backend/SQL names are not renamed. This terminology change does not introduce customer pagination.

- All eight customer/acquisition tables retain English domain entities: [Customer](domain/entities/customer.entity.ts), [Property](domain/entities/property.entity.ts), [Lead](domain/entities/lead.entity.ts), [LeadOrigin](domain/entities/lead-origin.entity.ts), [FunnelStage](domain/entities/funnel-stage.entity.ts), [LeadFollowUp](domain/entities/lead-follow-up.entity.ts), [CustomerContact](domain/entities/customer-contact.entity.ts), [CustomerPreference](domain/entities/customer-preference.entity.ts). Factories materialize typed values; unknown DTO validation belongs to sources.
- Customer responses preserve real stored lead, tax, source-system, external and registration metadata. Nullable portal `userId` is distinct from nullable `registeredByUserId`. No fabricated IDs, dates or null metadata. Normal profile writes contain only name/type/email/phone.
- Conversion requires **only** `leadId` and residential/commercial `type`. The server copies current lead values and atomically creates/links a customer. Repeating returns the linked customer, including inactive, without assuming that a newly supplied type changes it. The frontend does not merge, create accounts, infer funnel transitions or retry writes. Follow-up append does not change the lead stage.
- PUT sends every mutable field, including explicit nulls; nullable fields are replaced, not patched. Preference `propertyId: null` is customer-wide. Registration actors, timestamps and ownership come from server/path, not write bodies.
- Lead pagination reuses shared `PaginationParams` and `PaginationResponse`: defaults offset 0/limit 20; aligned nonnegative safe integer offsets map to zero-based `pagina`, with int32 page/size bounds. Returned effective metadata is adopted, including the backend maximum size 100. No invented filters. IDs must be positive int32; list IDs must be unique; response IDs and customer-scoped ownership are checked.
- `areaM2` is canonical two-place decimal text (for example `123456.70`) from the **bounded DECIMAL(8,2)** numeric wire value, range 1..999999.99. Only values round-tripping through that canonical representation are accepted. Writes validate decimal scale/range and emit JSON numbers. This is not a generic lossless arbitrary BigDecimal parser and does not preserve original wire trailing zeros. History order amounts likewise use bounded two-place decimal text, not arithmetic.
- Nullable values remain null, including redacted history fields. Zoned backend ISO timestamps become `Date` instants; local schedule/date fields remain strings. Backend `Fechas` supplies the offset; no operational timezone is selected. [History projections](domain/entities/customer-history.ts) preserve schedule/team information and separate page totals. Their server module scopes must not be interpreted as a frontend ACL or proof of a complete customer history.

## Security, errors and state

All sources use `HttpClient`, validated `API_URL`/origin policy and the existing auth interceptor. They do not read credentials or attach their own Bearer header. Every request disables transfer cache; SSR or missing/invalid origin fails closed with `UNCONFIGURED` and no HTTP. No config/origin/auth behavior, route, UI, dependency or backend file was changed.

Input violations return `INVALID_INPUT`; malformed success DTOs return `INVALID_RESPONSE`. HTTP 400/401/403/409/0 map to `INVALID_INPUT`/`UNAUTHENTICATED`/`FORBIDDEN`/`CONFLICT`/`NETWORK`. HTTP 404 uses `CUSTOMER_NOT_FOUND`, `PROPERTY_NOT_FOUND`, `LEAD_NOT_FOUND` or generic `NOT_FOUND` according to resource; other transport/server errors return `UNEXPECTED`. Raw backend messages are never exposed or logged. Existing `CLIENTE_LEER/CREAR/ACTUALIZAR/DESACTIVAR` permissions and per-module history scope remain server-authoritative; conversion requires create and update. No frontend role-name inference or new permissions.

Authorized property access instructions and door codes are preserved, validated and never logged. This does not grant new portal access. Cancellation unsubscribes requests and suppresses feedback; **it cannot roll back dispatched server writes**. There is no automatic mutation retry, demo/network fallback or seeded real catalog.

`CustomersStore` remains root-provided, with its existing small list/detail/write API and an explicit `setCustomerStatus` action instead of physical deletion. Only confirmed responses change state. Its list contains active profiles; confirmed deactivation removes that profile only from this projection, retaining an inactive selected detail, not physically deleting a record. Reactivation can restore the confirmed active profile, and subsequent list loads replace the projection with server results. There are no optimistic totals or inactive-catalog claims.

The existing Auth session-read-scope fences logout, expiry and identity/fixed-session-deadline replacement: state clears, pending requests unsubscribe and old completions cannot repopulate sensitive state or feedback. Same-session token renewal does not clear. Reads/writes are deferred until subscription, consumers own subscriptions, and root destruction cancels scope observation. SSR dispatches no store work. This is minimal compatibility/session safety, not a query-cache redesign.

`CustomerInMemorySource` remains explicitly **unwired test/demo only**, including its old local delete behavior. It is never a production repository or HTTP fallback. The obsolete production delete use case and its test are retired.

## Verification boundary

Focused official Angular Vitest tests use `HttpTestingController`, isolated fixtures/subjects and fake auth contracts. They exercise method/path/query/body mapping, all response values, errors/invalid DTOs, owner/ID/page checks, cancellation, SSR/configuration safety, application delegation, composition and store session fencing. See the implementation handoff for observed exact commands/results rather than inferring a current pass from this document.

Real authenticated HTTP/CORS, browser/keyboard/responsive acceptance, real MySQL concurrency/rollback and full production/SSR build acceptance are **not claimed**. Parent integration owns broad suite/build and independent risk verification (sensitive data/authorization and delete/response contract migration).
