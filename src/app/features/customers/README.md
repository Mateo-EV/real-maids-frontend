# Customers and acquisition — real HTTP application boundary

M03/RF03/HU03 and RF12/HU12 now have customer HTTP sources, explicit root repositories, stateless named `*UseCase.execute()` actions and session-scoped root presentation stores. The P04 list and WP3 create/edit/deactivate actions are source-connected at protected `/admin/customers`, reached through the existing **CRM** sidebar entry. The user reported manual acceptance of WP2; this is not agent-observed exhaustive browser/CORS evidence. Corrected WP3 visual/manual/live/browser acceptance and WP4 detail/properties remain pending. Acquisition still lacks a more specific inherited RF/HU identifier; this implementation follows the approved customer integration scope, not an invented requirement.

Required contract: backend `feat/customer-pagination`, commit `f7988fbf3c1ffb44ce0e98cf6909ad3d7e1a6d4e` or newer, including the extended customer metadata from `68fd59d`. Evidence: actual controllers, `CaptacionDtos`, `ClienteRelacionDtos`, extended `ClienteResponse`, `PropiedadRequest/Response`, `AtencionDtos.HistorialClienteResponse` and `HistorialClienteService`. Small feature-local pure helpers share repeated DTO/input checks; no generic CRUD base or cache framework was added.

## Customer page contract (S2/S4)

`CustomerRepository.findPage(query)` delegates to the root `CustomerHttpSource`; stateless `ListCustomersUseCase.execute(query = {})` returns `PaginationResponse<Customer>` directly. The legacy in-memory `findAll()` remains unwired fixture-only; there is no production whole-list fallback or client slicing.

| Boundary      | Contract                                                                                                                                                                                                                                                                                                                  |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Angular input | Shared `PaginationParams`: optional offset/limit, defaults 0/20. Offset must be a nonnegative safe integer aligned to positive safe integer limit; emitted page and size must fit int32. Invalid input fails before HTTP.                                                                                                 |
| HTTP          | `GET /api/clientes?pagina=offset/limit&tamanio=limit`, transfer cache disabled. Backend defaults page 0/size 20, normalizes negative pages to 0 and clamps size to 1..100; Angular rejects negative inputs rather than sending them.                                                                                      |
| Response      | `{ contenido: ClienteResponse[], pagina, tamanio, totalElementos, totalPaginas }`. Adopt `items=contenido`, `total=totalElementos`, `offset=pagina*tamanio`, `limit=tamanio`, including effective size 100 after a larger requested size. This maximum belongs to this backend contract, not a changed shared normalizer. |
| Validation    | Reject old unpaged arrays, malformed metadata, mismatched page identity, impossible row counts, duplicate IDs and inactive rows. Out-of-range pages retain their actual offset/limit and positive totals with empty rows; no local clamp or fabricated global empty result.                                               |

## Read-only customer list (WP1–WP2)

Users and CRM consume shared `CatalogFrame` for consistent hierarchy, header/actions, responsive table/cards and footer. Global styles switch records at 64rem of available container width. Users keeps navigation/KPIs outside and projects feature-owned filters; CRM adds no invented filters/KPIs. The reference guides functionality/content, not visual authority.

Both lazy routes call shared `provideCatalogToast()`, each owning HotToastService, ViewService and config together for its body overlay. Toast CSS stays global in `angular.json`, without root provider movement or a direct Users-feature import. The exact CRM label and model/API/store/session behavior remain unchanged.

The page starts at offset 0/limit 20 and shows official name/type/email/phone in a desktop table and mobile cards. WP3 adds create plus labeled edit/deactivate actions on both layouts, using the selected loaded record. There are no detail/property launchers, search/status/tag filters, invented metrics or inactive catalog. Missing contact values are labeled unregistered. Shared table pagination uses server total and effective offset/limit for ranges and subsequent navigation, without local slicing or an automatic duplicate fetch just to adopt metadata.

`selectQuery()` is read through a computed projection; `observeQuery()` subscriptions belong to the page and are replaced/cancelled on navigation/destruction. Root store lifetime, session fencing, two-minute TTL, shared reads and invalidation refresh remain unchanged. Loading, verified empty, initial error/retry, same-key stale refresh/error and unrelated-query isolation are separate visible states; safe Spanish errors never expose raw backend text.

The no-local-clamp rule above belongs to transport/store response preservation. The **page** may issue one different corrective query after a successful empty page with positive total and offset >= total: `floor((total - 1) / effectiveLimit) * effectiveLimit`, retaining effective size. It never rewrites a response or loops if the second page is also out of range. Only a new user navigation/retry resets that allowance. A total of zero is a verified empty catalog; a positive-total empty page remains a distinct out-of-range state.

Repeatable acceptance script (authorized non-sensitive records only): enter IAM → CRM, verify initial paging and returned ranges, navigate next/previous, exercise denied/network/empty and stale retry states, then return to IAM. Unit/router checks cover these contracts and cancellation/session clearing, not actual live auth/CORS or rendered Chrome/Edge/Firefox keyboard/mobile behavior. ## Connected profile actions (WP3)

M03/RF03/HU03/P04 and RNF01/RNF08–RNF10/RNF12: the local Signal Forms editor creates or replaces name/type/email/phone only. It trims these text inputs, requires a nonblank name up to 150 characters and residential/commercial type, validates optional email up to 120 and phone up to 30 with the source's accepted patterns, and explicitly sends null for blank contacts. This normalization is editor-owned: the current HTTP source validates but does not trim input. No metadata, account or status is included in profile writes.

Deactivation identifies the captured customer and confirms desired `false`; there is no physical deletion, toggle, inactive discovery or reactivation launcher. Both dialogs block duplicates, Cancel, Escape and outside dismissal while pending; idle dismissal remains available. Actionable inline alerts preserve drafts on failure; a route-local success toast announces only confirmed writes, fenced by owner/session lifetime, without consuming root successMessage or importing the Users feature. No mutation is automatically retried. Existing active observers refresh once after confirmed invalidation; rows/totals stay server-owned until that read completes, including refresh failure.

Page and dialog destruction cancel owned subscriptions, including the overlay's closing-animation interval. Session replacement/expiry/logout cancels work and suppresses stale feedback; same-session renewal preserves pending work. Cancellation cannot roll back dispatched backend writes. No root feedback is cleared on opening/closing a dialog.

## Types and write semantics

Angular uses `Lead`, `LeadOrigin`, `LeadFollowUp` and `leadId` internally, including quote and web-form links. Sources translate the unchanged Spanish `idProspecto`, `/api/prospectos` and `/api/catalogos/origenes-prospecto` wire contract; backend/SQL names are not renamed. Customer pagination does not change those Lead wire boundaries.

- All eight customer/acquisition tables retain English domain entities: [Customer](domain/entities/customer.entity.ts), [Property](domain/entities/property.entity.ts), [Lead](domain/entities/lead.entity.ts), [LeadOrigin](domain/entities/lead-origin.entity.ts), [FunnelStage](domain/entities/funnel-stage.entity.ts), [LeadFollowUp](domain/entities/lead-follow-up.entity.ts), [CustomerContact](domain/entities/customer-contact.entity.ts), [CustomerPreference](domain/entities/customer-preference.entity.ts). Factories materialize typed values; unknown DTO validation belongs to sources.
- Customer responses preserve real stored lead, tax, source-system, external and registration metadata. Nullable portal `userId` is distinct from nullable `registeredByUserId`. No fabricated IDs, dates or null metadata. Normal profile writes contain only name/type/email/phone.
- Conversion requires **only** `leadId` and residential/commercial `type`. The server copies current lead values and atomically creates/links a customer. Repeating returns the linked customer, including inactive, without assuming that a newly supplied type changes it. The frontend does not merge, create accounts, infer funnel transitions or retry writes. Follow-up append does not change the lead stage.
- PUT sends every mutable field, including explicit nulls; nullable fields are replaced, not patched. Preference `propertyId: null` is customer-wide. Registration actors, timestamps and ownership come from server/path, not write bodies.
- Customer and Lead pagination reuse shared `PaginationParams` and `PaginationResponse<T>` directly, without duplicate page types: defaults offset 0/limit 20; aligned nonnegative safe integer offsets map to zero-based `pagina`, with int32 page/size bounds. Returned effective metadata is adopted, including the backend maximum size 100. No invented filters. IDs must be positive int32; list IDs must be unique; response IDs and customer-scoped ownership are checked.
- `areaM2` is canonical two-place decimal text (for example `123456.70`) from the **bounded DECIMAL(8,2)** numeric wire value, range 1..999999.99. Only values round-tripping through that canonical representation are accepted. Writes validate decimal scale/range and emit JSON numbers. This is not a generic lossless arbitrary BigDecimal parser and does not preserve original wire trailing zeros. History order amounts likewise use bounded two-place decimal text, not arithmetic.
- Nullable values remain null, including redacted history fields. Zoned backend ISO timestamps become `Date` instants; local schedule/date fields remain strings. Backend `Fechas` supplies the offset; no operational timezone is selected. [History projections](domain/entities/customer-history.ts) preserve schedule/team information and separate page totals. Their server module scopes must not be interpreted as a frontend ACL or proof of a complete customer history.

## Security, errors and state

All sources use `HttpClient`, validated `API_URL`/origin policy and the existing auth interceptor. They do not read credentials or attach their own Bearer header. Every request disables transfer cache; SSR or missing/invalid origin fails closed with `UNCONFIGURED` and no HTTP. The list adds only its route/UI consumer; config/origin/auth behavior, dependencies and backend files remain unchanged.

Input violations return `INVALID_INPUT`; malformed success DTOs return `INVALID_RESPONSE`. HTTP 400/401/403/409/0 map to `INVALID_INPUT`/`UNAUTHENTICATED`/`FORBIDDEN`/`CONFLICT`/`NETWORK`. HTTP 404 uses `CUSTOMER_NOT_FOUND`, `PROPERTY_NOT_FOUND`, `LEAD_NOT_FOUND` or generic `NOT_FOUND` according to resource; other transport/server errors return `UNEXPECTED`. Raw backend messages are never exposed or logged. Existing `CLIENTE_LEER/CREAR/ACTUALIZAR/DESACTIVAR` permissions and per-module history scope remain server-authoritative; conversion requires create and update. No frontend role-name inference or new permissions.

Authorized property access instructions and door codes are preserved, validated and never logged. This does not grant new portal access. Cancellation unsubscribes requests and suppresses feedback; **it cannot roll back dispatched server writes**. There is no automatic mutation retry, demo/network fallback or seeded real catalog.

`CustomersStore` remains root-provided with caller-owned observables and an explicit `setCustomerStatus` action instead of physical deletion. `loadCustomers(query?, force=false)` selects a server-page projection with verified `total`, `offset`, `limit` and effective `currentQuery`, never a complete catalog. Unknown totals/metadata remain null, distinct from a verified empty collection or an out-of-range page with a positive total. Same-query expired/forced reads retain verified rows while refreshing; another query selects only its own entry. `readPage`/`readCustomer` perform reads, `selectQuery`/`selectCustomer` are pure projections, and `observeQuery`/`observeCustomer` pin active entries through caller-owned subscriptions. Detail selection is independent of page reloads. Session invalidation completes observation subscriptions and releases their active-key pins; a consumer entering a different session must create a new subscription.

Confirmed create/update/deactivate/reactivate/account-link responses **invalidate freshness**, retaining verified same-query rows and server metadata as stale until revalidation. Matching cached detail adopts the confirmed server profile and becomes stale, including inactive detail. Active observation subscriptions refresh once per invalidation; inactive entries never self-refresh. Writes never append/splice page rows, adjust totals, infer sorted membership or start an orphan subscription. Failed writes leave verified rows, counters and selected detail unchanged apart from feedback. Invalidation and session generations fence older reads; callback-triggered session changes must not allow subsequent old-session feedback or cross-store effects. No-argument reload defaults to offset 0/limit 20 until a verified effective query exists, then reuses it, including after invalidation or failed reload. Reload failure does not replay a confirmed write; totals always come from the server. The previously excluded read TTL is now explicitly approved; see the presentation freshness policy below.

The existing Auth session-read-scope fences logout, expiry and identity/fixed-session-deadline replacement: state clears, pending requests unsubscribe and old completions cannot repopulate sensitive state or feedback. Same-session token renewal does not clear. Reads/writes are deferred until subscription, consumers own subscriptions, and root destruction cancels scope observation. SSR dispatches no store work. Session safety is shared with the other capability stores; TTL remains a presentation freshness policy, not an authorization decision.

`CustomerInMemorySource` remains explicitly **unwired test/demo only**, including its old local delete behavior. It is never a production repository or HTTP fallback. The obsolete production delete use case and its test are retired.

## Presentation freshness policy

By explicit user approval, customer reads follow the existing SignalStore, shared `createReadResource` and auth-owned `createSessionReadScope` pattern (M03/RF03/HU03, RF12/HU12, RNF09/RNF10/RNF12).

| Root store                 | Read scope                                            | Success TTL |
| -------------------------- | ----------------------------------------------------- | ----------- |
| `CustomersStore`           | Server customer pages and individual customer details | 120000ms    |
| `CustomerPropertiesStore`  | Properties per customer                               | 120000ms    |
| `CustomerRelationsStore`   | Separate contacts and preferences per customer        | 120000ms    |
| `CustomerAcquisitionStore` | Origins and funnel-stage catalogs                     | 120000ms    |
| `CustomerAcquisitionStore` | Lead pages/details and follow-ups per lead            | 30000ms     |
| `CustomerHistoryStore`     | Customer history by customer and requested limit      | 30000ms     |

Freshness is checked on consumer reads, never by polling. Only successful current responses renew TTL; a failed refresh preserves verified same-key data with a retryable error. Forced retries bypass freshness. Identical in-flight reads share ref-counted cancellation; a caller unsubscribing does not cancel other consumers. Each consumer owns its subscriptions, and query/owner results remain separate rather than a singleton current catalog. Bounded histories protect in-flight entries; selecting a result alone is not a lifecycle subscription.

Confirmed writes invalidate affected reads and fence older completions without replaying mutations or inferring sorted page membership/totals. Cross-capability invalidation covers customer snapshots in history and customer pages after lead conversion. Read freshness never grants permissions, proves revocation or replaces backend validation. The customer page explicitly subscribes and releases reads on teardown; other consumers must do the same. These stores do not establish acceptance of the remaining P04 screens or live backend behavior.
