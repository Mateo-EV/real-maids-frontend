# Product scope and journeys

The Real Maids frontend is a responsive web application for managing cleaning services internally and giving customers a portal to follow their requests and services and contact customer support. This guide preserves the functional plan; it does not certify implemented features. See [the Spanish project overview](../README.md) for onboarding and current status, and [agent instructions](../AGENTS.md) for technical, security and quality rules.

## Current delivery boundary

P01 (M01/RF01/HU01) has a T2 candidate adapting documented login to nested `usuario`, access/refresh credentials and strict runtime profile/lifetime validation. The user explicitly superseded memory-only storage with temporary localStorage persistence for both credentials: versioned, backend-origin-bound and browser-only, with acknowledged JavaScript/XSS exposure. No profile or permission authorization is trusted from storage; reload uses real `GET /api/auth/me`. Access expiry can renew via public JSON refresh, using single-flight and origin-wide Web Locks with fail-closed behavior when unavailable. Rotation cannot extend the original session deadline. Source invalidation/renewal reaches the root store through repository/application contracts. Explicit logout clears locally immediately and sends a bounded best-effort credential snapshot to documented logout; offline failure is not reported as remote revocation success. Login replacement, cancellation, expiry and destruction do not silently perform remote logout. The functional Bearer interceptor is configured explicitly and limited to validated API-origin `/api/` paths; public auth/internal requests skip renewal and no request is replayed after 401. SSR/prerender does not access browser storage, create shared credentials, request auth or transfer-cache tokens. The profile uses returned IDs/name/role/language/permission strings, never role-name/JWT inference; unused last access is not assigned an invented null. Development permits the existing localhost:8080 API origin; production remains unconfigured until an approved HTTPS origin is set. ### Backend sessions — T5

M02/RF02/HU02/P03 restores Sessions grouped under users with native keyboard-accessible `<details>` disclosures, name/email search (USR-ID as secondary text), Todos/Con sesiones/Sin sesiones filters and local pages of five users. There is no raw user-ID entry; local controls never refetch HTTP. A stateless application use case delegates one global array read. The HTTP source makes exactly one `GET /api/sesiones` request at `pagina=0&tamanio=1000`, accepts a positive safe-integer effective response size up to 1000 even when it differs from the requested size, validates page counts and content length against that effective size, and preserves DTO, unique-ID, owner-identity, ordering and at-most-one caller-relative current-flag validation, then returns only entities. It never fetches additional pages even when totals exceed the cap; the approved size is not a documented backend maximum. The root store replaces records only after successful validation. Read failures remain visible with retry and preserve prior records, never false zero. During loading/error/cancellation, row counts remain unverified and presence filters are disabled. Absence comes from returned session records, never local clock expiry.

Users receive groups, including users without returned sessions after a successful read. Owners absent from the users array retain their real server names/emails and session records without fabricated profiles or N+1 requests. The UI treats both arrays as all available records, without incomplete-catalog or technical outside-catalog warnings. User loading/errors remain distinct from session absence. Returned session identity, device, IP and UTC dates remain authoritative. Navigation and metrics derive counts solely from the session array, independently of local filters. Superseded component reloads and destruction cancel owned reads; stale completions cannot overwrite newer state. Post-revoke reads repeat the fixed global request without optimistic count patches or replaying writes; refresh failure stays visible even after a confirmed revoke.

The caller-relative `actual` field identifies the current session; no token/storage marker is correlated with a server session ID. Its individual revoke is blocked with guidance to use Logout; backend 400 remains authoritative. Confirmation identifies user/device and prevents duplicate submission and pending dismissal. Empty successful 200/204 revocation responses are accepted, including already closed/expired sessions. Per-user reads remain available through repository/use-case contracts; bulk revoke also remains in the store, without a new UI launcher. Bulk revoke of the caller preserves the current session per the backend contract. Component cancellation suppresses late feedback but cannot roll back a dispatched backend mutation.

Root store lifetimes, stateless use cases and the distinct useExisting repository/source boundary remain (RNF09/RNF10). SSR does not dispatch session HTTP requests or transfer-cache them. The old registry is unwired test/demo data, never a fallback. UTC display does not select an operational timezone. Live authenticated backend/CORS and Chrome/Edge/Firefox visual, keyboard and responsive acceptance remain pending (RNF06/RNF08/RNF12).

The editor follows documented password validation: creation requires 8–64 characters with uppercase, lowercase and a digit, while a blank edit preserves the existing password. Password bytes are never trimmed or stored in user identity. Create sends the documented profile/password fields; editing sends profile `PUT`, desired status `PATCH` only when changed, then optional `PUT /api/usuarios/{id}/password` with `passwordNueva`. This sequence is not atomic: later failure returns `PARTIAL_UPDATE`, refreshes server profile state and does not show success. Cancellation after dispatch cannot guarantee rollback; no writes are replayed automatically. Transport/DTO failures return safe typed errors, including forbidden, duplicate email and not found, without raw backend details. Browser/CORS/authenticated backend acceptance and visual/responsive/keyboard checks in Chrome, Edge and Firefox remain pending; simulated HTTP tests and a build do not certify live behavior.

M03 has a `customers` domain, five query/CRUD use cases, an in-memory adapter and a presentation store, but no P04 route or UI. It does not deliver customer management/history to users or define backend DTOs, persistence or email uniqueness. All other screens and the customer portal remain planned. IAM users/role catalog HTTP adapters are the T3 candidate; sessions and audit have T5–T6 HTTP adapters; enforced frontend role navigation, E2E and CI/CD remain absent; T4 connects permission catalog/assignment HTTP operations; auth persistence/transport is the T2 candidate, not a completed IAM capability; production deployment is unverified. Existing unit tests are not a claim of a newly verified pass or fixed test count.

### Dynamic backend role permissions — T4

M02/RF02/HU02/P03 connects Roles/RBAC through stateless catalog/query/save use cases, a root SignalStore and a distinct repository token aliased with useExisting to the root implementation injecting its HTTP source (RNF09/RNF10). `GET /api/permisos` supplies read-only permission metadata; `GET /api/roles/{id}/permisos` supplies the actual assignment. IDs, codes, descriptions and module groups come from the backend, not fixed CRUD unions, illustration rows, guessed role IDs or configured flags. The old illustration source/dialog are unwired test/demo assets, never HTTP fallbacks.

Responsive module fieldsets expose labeled Signal Forms checkboxes, description/code/ID and explicit loading, empty and retryable error states. Assigned permissions absent from the catalog remain visible and selected until explicitly removed; they are never silently dropped. Changing roles discards a draft only after successful loading of both catalog and assignment. Superseded loads are cancelled and response identities checked; failed loads preserve the visible role/draft and block saving. Revisiting the retained section does not reload it.

Save confirms the affected role and concrete grants/removals, then sends atomic whole replacement `PUT /api/roles/{id}/permisos` with required `{ idsPermisos: integer[] }`; IDs are nonnegative and unique, and `[]` means no permissions. The returned role ID and assigned set must match the request before reporting success. Pending submission blocks duplicates and dismissal; 403 preserves the draft for explicit correction/retry, without automatic mutation replay. The backend prohibits changing ADMINISTRADOR, editing one's own role and granting unauthorized permissions; the frontend neither infers ACL from names nor assumes every `delSistema` role is uneditable. Changes apply from the next request according to the contract. Backend authorization remains authoritative. No role-management UI, navigation ACL, authentication mutation or translation is introduced. Sessions/audit have T5–T6 HTTP adapters; legacy simulations are unwired. RNF06/RNF08/RNF12 guide accessible controls and feedback; live authenticated backend/CORS and Chrome/Edge/Firefox keyboard/responsive acceptance remain pending.

### Read-only backend audit viewer and CSV — T6

Audit-specific RF/HU traceability is still missing from the inherited product plan. M02/RF02/HU02/P03 provides users-administration context, not new audit requirements; RNF06/RNF08/RNF09/RNF10/RNF12 guides navigation, responsive feedback and layering. The connected Audit section has a root SignalStore, read/detail/export use cases and an audit repository token aliased with useExisting to the root implementation injecting the root source.

The HTTP source reads `GET /api/auditoria`, with actor ID, inclusive UTC from/to days, entity/action and zero-based page/size parameters. Actor filtering uses local name/email search and a labeled native Helm selection from the already loaded UserStore catalog, without raw ID entry or per-keystroke HTTP. Email distinguishes equal names; only a selected option supplies the stable numeric userId, independently of search text. All actors clears that selection; clearing filters also resets search. The retained section preserves the choice, including temporary catalog gaps. Catalog loading and failure remain explicit, without completeness disclosures; historical/deleted actors may be absent from the users array. Audit rows, totals, detail IDs and raw export remain server-authoritative, never constrained by catalog membership. The viewer requests five records; filtered total and `totalGlobal` come from the backend, not loaded rows. Returned codes remain open strings; detail reads the chosen ID and validates identity and supplied changes. Superseded queries are cancelled; stale results cannot replace current state or global totals. Invalid input/DTOs produce safe typed failures. Legacy in-memory audit fixtures remain unwired, never HTTP fallbacks.

Desktop rows and mobile cards show backend actor, UTC timestamp, action, entity, record ID and IP/origin. Loading, empty, retryable query/export errors and pending controls remain explicit. `GET /api/auditoria/exportacion` returns raw CSV bytes for the filters, with a documented 10,000-record cap; export never rebuilds CSV from the cached page. The download adapter guards browser APIs for SSR, releases object URLs and reports initiation, not successful file saving. Actual response headers, spreadsheet-formula safety and browser download acceptance remain unverified.

This delivers read-only HTTP query/detail/export, not audit writes, a separate route, frontend durable persistence, security monitoring, immutability or actual hash/integrity verification. Navy primary actions and UTC deliberately remain instead of the screenshot's coral Save and UTC-5. Screenshot comparison and markup tests do not establish rendered fidelity; Chrome/Edge/Firefox visual, responsive, keyboard and actual download acceptance remain unrun.

## People and navigation

Planned actors are administrators, administrative staff, field staff and customers. A “boss” or otherwise authorized supervisory profile appears in the plan, but its relation to formal roles and permissions is unresolved; do not equate it with administrator.

Planned entry views are P02 for administrators, P06 for administrative staff, P09 for field staff and P11 for customers. These are not an ACL or implemented redirects. Actual permissions must be confirmed with the backend.

## Planned journeys

### Internal operations

1. Find or register a customer, retaining useful context and history (M03/P04).
2. Record a service request (M04/P05) and progress to a service order (M05/P06).
3. Schedule the order and assign field staff (M07/M08/P08).
4. Follow execution through completion and payment status; use reports/dashboard for oversight.

This is a navigation outline, not a specification of automatic conversions, payment collection or unconfirmed backend rules.

### Field staff

Open assigned services (P09), inspect the client, date/time and current state, then perform a permitted state update. Mobile layouts should prioritize readable cards and visible actions rather than copying administrative tables.

### Customer portal

Open “My requests and services” (P11), inspect details and follow progress, then access customer support (P10) when needed. Direct creation of a service request by a customer is unresolved and must not be assumed from the portal's name.

### Supervision and integrations

Use P02/P12 for indicators and reports within confirmed permissions. P13 may surface QuickBooks synchronization status, errors and permitted retries; integration logic and reconciliation remain backend responsibilities.

## Business states

Keep the existing Spanish state labels until contracts and localization are confirmed.

- **Normal order sequence:** `Pendiente → Programada → En proceso → Completada → Pagado` (pending, scheduled, in progress, completed, paid).
- **Cancellation:** an alternative exit for orders; allowed source states and other exceptional transitions/reopenings remain undefined.
- **Customer support sequence:** `Recibida → En revisión → Resuelta → Cerrada` (received, under review, resolved, closed).

Support states are independent of order states. Do not invent request states or treat a support case as a service request.

- Whether customers can directly create service requests.
- Formal meaning of “boss,” final ACL and permission-based entry/navigation.

Auth refresh/revocation adapters do not certify live backend acceptance. Review private-route render modes when fuller backend sessions are introduced.

Resolve these with explicit product/technical decisions and actual backend evidence. Update this guide when a route, consumer or integration changes delivery status; keep the useful identifiers without expanding this into a duplicate implementation matrix.
